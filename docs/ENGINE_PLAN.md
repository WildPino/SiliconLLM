## Principles (project law, carried over)

- **Correctness before speed.** The fp32 C core built in E1 is the permanent regression harness: every later optimization lands only after parity against it is proven. An optimization without a reference is an unfalsifiable bug.
- **One variable per stage.** Each stage changes exactly one thing and has pre-registered gates. No gate is loosened after seeing results (anti-Goodhart; the only legitimate post-hoc move is tightening).
- **No `-ffast-math`** (Phase 35 determinism law). Toolchain: `clang -O3 -mavx2 -march=znver2`. Single-thread first; threads are a later, separate variable.
- **Decode hygiene locked:** greedy, repetition penalty 1.2 over a 128-token window, no top-p.
- **Honest scope:** at ~8.3M sandbox scale everything is cache-resident — E1-E3 validate *correctness* and *kernel-level* speed, not the streaming architecture. The two-pool layout (resident ≤16MB @ ~100 GB/s + DRAM-streamed experts @ ~28 GB/s, per probe-4) is exercised from E4 on and pays at scale-up.
- **Unit-exactness does not compose to system correctness** (E4 lesson, elevated to project law): a bit-exact kernel gate can pass while staging buffers / scale-apply corrupt the system (E4: a `g_xq[HID_E]` overflow cost +0.15 BPB while the kernel self-test stayed green; caught only by end-to-end parity + per-block diagnostics). Every rung keeps an end-to-end parity gate; kernel self-tests are necessary, never sufficient.

## Stages and pre-registered gates

### E1 — fp32 reference core (target model: `sp58_base.pt`, ~8.3M Arch-A: D256 N96 H8 L6, SWA@5, gated-dReLU ternary MLP)
1. **Exporter** (Python): checkpoint + tokenizer → versioned binary format (magic, arch header, fp32 tensors; the ternary MLP is exported *both* dequantized-fp32 (E1 path) and packed ternary+per-row scales (ready for E2)). Tokenizer (BPE-1024 vocab + merges) embedded or sidecar.
2. **C forward pass:** embedding → 6 blocks (Mamba-1 selective-scan semantics *exact*, SWA at its layer with its trained window, gated-dReLU MLP) → head → logits. Token-by-token AR, O(1) state.
3. **Decode:** the locked hygiene recipe.
4. **GATES:**
   - **G1 golden-trace:** PyTorch dumps per-layer activations for a fixed 64-token sequence; the C engine must match layer-by-layer (max rel. err < 1e-3 per layer; report the error profile). This is both the gate and the debugging instrument for scan-semantics drift.
   - **G2 logit parity:** top-1 agreement ≥ 99.9% over ≥ 10K val tokens.
   - **G3 BPB parity:** engine BPB on the val slice within ± 0.002 of the PyTorch eval (0.8799).
   - **G4 tokenizer parity:** C BPE encoder produces identical token ids vs the Python tokenizer over the val corpus.
   - **G5 generation parity:** greedy+rep streams identical on fixed prompts; divergences acceptable only if traced to fp reorder (report, Architect judges).
5. **Perf baseline:** single-thread tok/s on the 3600X, recorded. **No optimization allowed in E1** — this is the "before" number.

**E1 CLOSED (2026-07-02) — all gates green.** G1 l2-rel err ~4e-7 per layer (max_abs ~1e-5 = fp reorder); G2 top-1 100.0000% (20480/20480); G3 BPB 0.879949, delta +0.000000; G4 zero mismatches over 975,712 tokens; G5 zero divergences over 600 greedy tokens (3 seeds, bit-identical). Baseline: **176.1 tok/s / 5678 µs/tok** single-thread fp32 exact-exp. Apparatus: `benchmarks/phase60/` (exporter `e1_export.py`, reference `e1_reference.py`, engine `e1_engine.c`; rerun `bin/e1_engine.exe --all`). Adjudicated notes: (a) G1's original per-element rel-err metric was diagnostically broken near zero (false 0.25 readings on ~1e-5 activations); the l2-relative-per-layer replacement is a metric fix, corroborated by three orthogonal untouched gates — not gate-loosening. (b) G5 parity is bit-exact only while generation ≤ seq: beyond that the recompute-from-zero *reference* cannot represent the stateful stream — a streaming (stateful) PyTorch reference will be needed for E5/long-context. (c) G4 is self-consistent with the training-data codec lineage — which is the correct parity target (match what the model was trained on).

### E2 — ternary LUT MLP (probe-1 kernel lands) — ACTIVE
Pack ternary weights into the pshufb-LUT path (kernel from `benchmarks/phase57/phase57_lutbench.c`) for the three MLP matvecs (gate/up/down); packed ternary + per-row scales are already in the E1 export format. One variable: the MLP matvec path. Everything else untouched.

**Surfaced question (pre-registered before results):** the LUT requires **quantized activations** (int8, per-token absmax) to build the byte tables — but the model was trained with fp activations (only weights fake-quantized). Activation quantization is therefore a *new* inference-time error whose model-level cost has never been measured (probe-1 proved the kernel bit-exact vs an *integer* reference; quality was measured with fp activations). It is gated, not assumed.

**GATES:**
1. **Kernel bit-exactness:** LUT matvec bit-exact vs the scalar integer reference (probe-1 discipline).
2. **Quality:** BPB delta vs E1 ≤ **+0.005** (half the ternary cost itself). If it fails, the gate is NOT loosened; documented fallback = exact ternary add/sub path on fp32 activations (no multiplies, exact, slower than LUT), and/or escalation: per-group activation scales, int16 accumulation, activation-QAT in a future train.
3. **Agreement:** top-1 vs E1 ≥ 99% over ≥10K val tokens (greedy streams may legitimately diverge — logits change; report).
4. **Timing, Amdahl-explicit:** per-component time breakdown (scan / SWA / MLP / head / exp) **before and after** — the E1 baseline (~176 tok/s ≈ ~2 GFLOP/s effective) is very likely dominated by the exact-exp scan, not the MLP, so the honest E2 headline is the **MLP kernel time** (anchor 4.2-5.0×); the end-to-end tok/s gain is bounded by the MLP time share and is expected to be muted. Pre-registered deflation.

**E2 CLOSED (2026-07-02) — all four gates green.** `benchmarks/phase60/e2_engine.c` (reuses the E1M1 format; packed ternary already present). Activations quantized per-token absmax to **[-63,63]** (the widest range fitting int8 for ternary g=2 → best precision, kernel untouched); gate/up share one LUT build. Results: G1 kernel bit-exact, worst `|S_lut−S_ref|=0` over 2.76M dot-products; **G2 BPB delta +0.000037** (E1 fp32 0.841172 vs E2 LUT 0.841209, same 100K slice — the activation-quant concern resolved negative, 135× inside budget); G3 top-1 **99.7363%** (10213/10240); **G4** fp32 MLP = 811 µs/tok = **14.0%** share, scan-exp = **83.5%** (the surfaced hypothesis confirmed — the scan, not the MLP, is the bottleneck), LUT MLP = 378 µs/tok → **MLP kernel 2.14× faster** (incl. per-token quant+LUT-build+dequant), end-to-end 172.7→179.5 tok/s = **1.04×** (Amdahl-muted, exactly as pre-registered). Honest deflation: 2.14× < the 4.2-5× pure-kernel anchor because per-token LUT-build/quant/dequant overhead at ~8.3M-small dims is included — amortizable under block-decode (E5). **Cross-stage note:** the real bottleneck is the exact-exp selective scan (83.5%); a future scan-exp optimization (gated poly/LUT exp, parity-gated as an approximation) is the highest-leverage speed lever, orthogonal to the MLP path.

**Adjudication (Architect, 2026-07-02): E2 CLOSED, 4/4.** (a) The end-to-end +4% is within run-to-run noise (the scan itself varied +5% between the two runs) — the robust E2 claim is the component-level **2.14×**, and the absolute BPB shift vs E1's G3 (0.8412 vs 0.8799) is a slice change (100K vs 200K), not a regression: the valid comparison is the same-slice delta (+0.000037). (b) The **[-63,63]** activation range is endorsed: widest int8-safe range for ternary g=2 (2·63=126<127) = maximum free activation precision with the kernel bit-exactness untouched. (c) **Scale-up caveat, pre-registered now:** the ~zero activation-quant cost holds at ~8.3M/D256/TinyStories; per-token absmax int8 degrades when outlier channels emerge with model size — re-measure at scale-up, with per-group scales as the known escalation. (d) The scan-exp lever is approved as its own stage **E3.5** (below).

### E3 — activation-sparsity skip (predictor-free) — ACTIVE
Compute the gate matvec first; for gate≤0 units skip the up work, and skip down columns where h=0. The skip is **exact in the integer LUT domain** (skipped rows/columns contribute exactly zero), so the gate is stronger than "numerically identical". Same model (`sp58_base` — one variable = the skip mechanism). **Layout rule (ρ-law in the data layout):** store W_down transposed (per-hidden-unit columns contiguous) so column-skip is contiguous-chunk skip, not strided gather.

**GATES:**
1. **Bit-identical logits vs E2** on the val slice + golden trace (exactness of the skip).
2. **Measured sparsity per layer** (gate% and h% at inference) reported against the probe-2 anchors (79% gate / 92% hidden).
3. **MLP time before/after.** Anchor ~2.12× applies to the *matvec portion only* — the LUT-build/quant/dequant overhead does not shrink with sparsity, so measured MLP speedup < 2.12×. **Pre-registered deflation.** End-to-end will barely move (MLP is 6.8% post-E2): E3's value at sandbox is *correctness of the mechanism + measured kernel shrink* — thesis validation, not speed.
4. **Optional E3b (Architect decision after gates pass):** export the Phase 58 coherence-trained checkpoint (+reg, BPB 0.8801) and measure block-granular skip yield in-engine — the in-silico test of whether the block-structured sparsity recipe pays on real hardware.

**E3 CLOSED (2026-07-02) — gates green.** `benchmarks/phase60/e3_engine.c`. Gate = full LUT (predictor); **up row-skip** (row-major codes → scalar-LUT dot for gate>0 rows only; gate≤0 → h=0 exactly); **down tile-skip** (tile-major codes → iterate hq≠0 tiles only; a tile is a contiguous Mpad block, so it is chunk-skip not strided gather — layout satisfies point #4 without a separate transpose). Exact by construction (integer S associative). Results: **G1 bit-identity: 0 mismatches over 5,242,880 logit values, worst |diff|=0.0**; sparsity gate mean **78.5%** (anchor 79%), h mean **93.5%** (anchor 92%), down tile-skip **87.7%**; MLP time 370.8→319.4 µs = **1.16×**, end-to-end ≈ flat (188.7→192.3 tok/s). **Honest headline = weight-bytes touched, not compute-time:** gate 100% + up 21.5% + down 12.3% = **44.6% → 2.24× fewer MLP weights touched/token** (≈ the 2.12× anchor, slightly better via h 93.5%). Compute-time is only 1.16× because at cache-resident ~8.3M dims dense-pshufb beats scalar-sparse (up-skip), the gate is unskippable (1/3), and quant/LUT-build overhead is fixed — the skip's real value is **bandwidth (weights not streamed), invisible in a cache-resident microbench, paying at scale-up (E4 two-pool)**, exactly the pre-registered scope. E3b remains available (block-structured `sp58_reg.pt` → the up-row-skip pays at 32-block granularity).

**Adjudication (Architect, 2026-07-02): E3 CLOSED.** The bit-identical bar (0 mismatches / 5.24M logits, worst |diff| = 0.0) is the strongest gate in the plan and passed clean. The in-engine sparsity reproducing the training-measured anchors (78.5/93.5 vs 79/92) is itself a transfer validation: the probe-2 property is real on silicon. Endorsed reading: the *composing* number is **2.24× fewer MLP weight-bytes touched per token** — that is what multiplies with the two-pool streaming at scale-up; the 1.16× compute time is the honest cache-resident reality (SIMD-dense beats scalar-sparse at small dims; the gate matvec is the non-skippable predictor). ### E3.5 — fast-exp scan path (deterministic approximation, parity-gated) — ACTIVE

GATES: BPB delta vs E1 ≤ +0.001; top-1 vs E1 ≥ 99.9%; golden-trace error profile reported; scan time before/after + new end-to-end tok/s. Methodological payoff: shrinking the dominant scan share sharpens the end-to-end signal of every later stage (E4/E5).

**Implementation guidance (Architect):** (1) *Range-aware validation first:* dump the observed input domain of the exp arguments (dt·A) from the golden trace; the approximation's max rel. error must be documented over that *observed* domain, not a generic one. (2) One versioned function, fixed coefficients, deterministic — reproducible by construction. (3) Vectorizing the scan loop that the poly-exp enables counts as the *same* variable (the scan-exp path); every other component untouched. (4) Pre-registered expectation, honest: if exp dominates the ~4.3 ms scan, end-to-end lands around ~450-650 tok/s (~2.5-3.5×); report what remains after.
