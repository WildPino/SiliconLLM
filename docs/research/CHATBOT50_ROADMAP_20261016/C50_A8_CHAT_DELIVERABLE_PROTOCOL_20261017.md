# C50-A8 protocol: tokenizer, chat template and interactive loop in C

17 October 2026. Cell A8 of the [CHATBOT50 roadmap](ROADMAP.md) §5: "C tokenizer verified
against the source tokenizer, chat template, interactive loop." A8 is a deliverable, not a
gate. This protocol fixes what "verified" means before any verification is run.

**Why now.** Everything A8 needs already exists: the engine's P0 path passed A3, and the
tokenizer is fixed by the checkpoint. A8 needs no long run and no owner action, while A4,
A6 and the A5 decision wait for the owner.
- **If the owner changes donor (COMMUNICATION item 3, option C):** the BPE, byte-level and
  template code carry over; the pre-tokenizer matcher and the template text do not.

## What is built

- **`c50_tok.h`, tokenizer in C.** It reads the vocabulary, token types and merges from the
  GGUF. They are equal to the source `tokenizer.json`: the A2 vocabulary check, and the 156,635
  GGUF merges compared equal to the source list today.
  It reproduces the source pipeline:
  1. **Added tokens:** the GGUF's 262 control and user-defined tokens are matched on the raw
     text, leftmost-longest, as the source's added vocabulary does (all of them have
     `normalized: false` and no strip flags).
  2. **NFC** on the remaining segments. The tables are generated from Python's `unicodedata`
     15.0.0 by `c50_a8_gen_unicode.py`.
  3. **The Split pre-tokenizer:** a hand-written matcher of the source regex, alternative by
     alternative, with its possessive and look-ahead semantics. `\s` is the Unicode White_Space
     set; `\p{L}` and `\p{N}` come from the same tables.
  4. **Byte-level mapping**, then BPE that merges the lowest-rank pair, leftmost first
     (HF `Word::merge_all`).
  5. **Decode** with the byte-level decoder: a token whose characters are all byte-mapped
     becomes those bytes, otherwise its UTF-8 bytes; the output is lossy UTF-8.
- **Chat template in C.** It covers the source Jinja template for system, user and assistant
  messages, with `thinking_option = 'off'` and `add_generation_prompt`.
  - Out of scope, with the reason stated in the tool: tools, tool calls, tool responses,
    and assistant content that contains `</think>`.
- **`c50_chat.exe`, the interactive loop.** It uses the A3 engine's forward on a P0-family GGUF.
  - Each turn is rendered by the template, encoded with special tokens recognised, prefilled,
    then generated until `<|role_end|>` (156895) or `<|endoftext|>` (156892), as in the source
    `generation_config.json`.
  - Sampling is greedy by default; `--temp` and `--top-p` take a fixed seed.
  - The KV cache keeps the generated IDs across turns. The conversation is not re-encoded:
    this matches what llama.cpp's server does, and differs from a full re-encode only when the
    model emits a non-canonical split. Turn boundaries are special tokens, so the boundaries
    themselves always tokenize the same way.
  - Context is capped at 8,192, where the loop stops and says so.

## Verification (fixed now; the tools print numbers, `c50_a8_verdict.py` applies the rule)

The reference is HF `tokenizers` 0.22.2 on the pinned `tokenizer.json`, plus jinja2 3.1.6
through `transformers` 4.57.6 `apply_chat_template` for the template.

| # | Check | Set | Pass |
| --- | --- | --- | --- |
| T1 | encode IDs equal | the 144 FIT document texts (`fit.jsonl`) | 0 mismatching documents |
| T2 | encode IDs equal | the A4 chat panel prompts (`a4_chat_panel_v1.json`) | 0 mismatches |
| T3 | encode IDs equal | stress set S (below) | 0 mismatches |
| T4 | decode bytes equal | the decode of every T1-T3 sequence, plus 2,000 random ID sequences (seed 20261016, length 1-64, IDs uniform over the 157,153 source IDs 0-157,152) | 0 mismatches |
| T5 | template text equal | conversation set C (below), text and IDs | 0 mismatches |
| T6 | loop smoke | 3 fixed prompts, greedy, 64 new tokens | runs, stops at EOS or the limit, prints CONFIG |

**Stress set S** (generated by `c50_a8_stress.py` from seed 20261016 before any comparison):
- 3,000 strings of 1-40 code points drawn from code points assigned in Unicode 15.0. Half of
  them are biased towards combining marks, Hangul jamo and syllables, CJK, emoji with ZWJ and
  variation selectors, and `\r`, `\n`, tab, NBSP and other White_Space.
- 1,000 strings that mix ASCII words, digit runs, the contractions `'s 'S 'll 'VE` (and the
  long s `ſ`), punctuation runs followed by newlines, whitespace runs at the end of the
  string, and added-token texts embedded inside and next to words.
- 500 strings whose NFC differs from themselves: decomposed Latin, Hangul jamo sequences and
  out-of-order combining marks.

**Conversation set C:** 12 fixed conversations, with and without a system message, 1-4 turns,
Italian and English, including empty content, newlines, and special-token text inside user
content. Each is rendered with `add_generation_prompt=True`.

**Not gated, reported:**
- 500 strings with unassigned code points or code points newer than Unicode 15.0. A
  mismatch there means the reference uses newer Unicode tables, not a bug.
- Greedy agreement of `c50_chat.exe` with `c50_llama_generate` on the same GGUF and the
  same T6 prompt IDs: the first divergence position. A3 already judged fidelity, and this is
  a smoke.

**Registered prediction (scored):**
- T1, T2, T4 and T5 pass on the first attempt.
- T3 has at least one mismatch on the first attempt, in NFC or in the possessive alternatives.
- **Rule for that case:** a T3 mismatch is fixed and the whole of T1-T5 is rerun.
- The first attempt's numbers are kept in the record.

**What this cannot say:** no rate (A7), no quality (A4/A7), and nothing about Unicode
versions newer than 15.0.
