## 5. Scaling n still requires routing, information and whole-token budgets

For top1, keeping the selected expert's cost fixed does not keep the entire
token cost fixed. The bookkeeping is

    t_token(n) = t_core + t_router(n) + t_selected(n) + t_other.
    b_token(n) = b_core + b_router(n) + b_selected(n) + b_other.

The required sustained 50 accepted tokens/s permits an average of 20 ms per
accepted token in the declared batch1 setting. RAM limits resident capacity;
measured routing,
physical memory traffic and all other stages determine whether that capacity
can be consulted within the token budget. A smaller stored expert bank does
not by itself prove a reduction in physical DRAM reads or token latency.

Winner preservation and normalization preservation are separate constraints.
For an ideal positive-exponential top1 router, let Z be the full normalization
sum and T the omitted positive tail, with scores and winner otherwise exact:

    p = exp(s_winner)/Z,
    p_hat = exp(s_winner)/(Z-T),
    p_hat/p - 1 = T/(Z-T).

The winner can be correct while this relative probability error is large.
In the selected conditional branch y=p*f, keeping the same winner and acceptance
gives

    y_hat-y = p_hat*(f_hat-f) + (p_hat-p)*f.

Thus a function-error certificate and a winner certificate alone do not bound
the routed contribution; the normalization error must also be bounded. These
are ideal algebraic identities, not a new certificate for the native rounded
router. Existing mass measurements remain the actual evidence.

Finally, increased n must retain more distinct, causally useful capabilities.
Controlled interventions and donor-relative held-out prediction, generation
and tasks must establish that gain on the same final artifact used for speed.
Counts, input ranks and output-energy shares cannot establish it. The current
bank11 compression inquiry resolves only one prerequisite in this chain.
