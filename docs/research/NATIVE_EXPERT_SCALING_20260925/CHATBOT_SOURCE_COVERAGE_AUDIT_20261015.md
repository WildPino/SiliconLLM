# Source-coverage capture: independent stored adoption audit

This protocol audits the completed 15 October source-coverage capture using CPU-only reads. It adopts **stored numeric and custody evidence** if every check passes. It does not run the donor, regenerate outputs, query a learner, or admit transfer, semantic task quality, native rate, DRAM behavior, or useful capacity.

## Acceptance checks

1. Rehash the producer report, binding, plan, adopted corpus, original producer holder/worker terminal and owned-process receipts, every bound input pin, and every declared output file. Check producer PID/create-time linkage and exit-zero receipts, exact directory inventory with no missing, extra, or partial outputs, producer limits and flags, and repeat all seals after numerical inspection. The producer's recorded OS/GPU peaks and duration are checked against its frozen caps; those readings remain producer witnesses.
2. Derive the selection independently from the adopted 624-case corpus and the original 48 used IDs: all remaining FIT/DEV input lengths at most 2,048, longest first, then source/split/ID. Demand the exact 432 plan cases and order, 360 FIT/72 DEV, 30 FIT/6 DEV for each of 12 sources, unique IDs/group keys, no overlap with the original groups, 104 excluded RESERVED rows, and 40 deferred LongAlign rows. Match the producer corpus order and every packet's metadata, messages, prefix digest, source row path/index, group key, and standalone case JSON. External reference answers are never treated as generated labels.
3. Recreate each input ID sequence with the local `ChatTokenizer` implementation using the captured Jinja chat template and tokenizer. Independently decode each generated ID sequence to its stored text. Enforce 1–256 output IDs, EOS IDs 11/228 only at the end, 2,304-position bounds, and exact teacher-forcing input IDs and positions. The two controls must retain 18 and 256 labels and identical generated IDs to their bound original cached packets.
4. Read every BF16 score file as a memory map, at most 16 rows at a time. Each 65,537-word row must decode to finite F32 values; the first-index argmax must be the recorded generated ID. Compare **every BF16 word** of each control to its bound original cached file. Verify 76,512 new label rows and the completion journal's exact equality with final corpus records and controls. The journal deliberately retains `original_posthash_complete=false`; the final report and this audit supply the later completed seals.
5. Demand identical stored `parameter_before.json` and `parameter_after.json` for all 411 names, shapes, and canonical BF16 SHA-256 values. Independently parse the source `model.safetensors` header and stream-hash each BF16 tensor byte range against the runtime binding, using bounded buffers. This verifies the stored source bytes independently of the producer's runtime `checkpoint_tensors` comparison.

The report's raw F32-to-BF16 losslessness, original GPU model parameter identities and versions, MuP constants in live model objects, GPU source execution, and GPU release before posthash cannot be independently reconstructed from stored BF16 files. They remain explicit producer witnesses even when their stored flags and receipts pass. First-index BF16 argmax is independently checked; raw F32 argmax is not. A passing decision is `INDEPENDENT_STORED_NUMERIC_PASS` with `quality_admissible=false`, and does not imply that a smaller learner reproduces donor behavior.
