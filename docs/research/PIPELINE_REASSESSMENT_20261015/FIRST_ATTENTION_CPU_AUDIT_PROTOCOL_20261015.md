# First-attention independent CPU audit

This separate auditor reads a completed `FIRST_ATTENTION_RANK_RESULT_V1` directory. It imports neither the rank producer nor its metric functions and never calls a GPU API. It must use the same pinned Python/PyTorch/psutil runtime named in the producer binding. The default pass is designed for a precision-floor stop: it needs only the 36 source BF16 and full-rank F32 trace pairs, not factors or candidate traces. Do not start it before `result.json` and `watchdog_done` exist.

Invoke with explicit paths and an exclusive report outside the producer directory:

```powershell
python benchmarks/native_expert_scaling/first_attention_cpu_audit.py --manifest results/native_expert_scaling/first_attention_source_20261015/manifest.json --binding results/native_expert_scaling/first_attention_source_20261015/rank_binding.json --output results/native_expert_scaling/first_attention_rank_20261015 --report results/native_expert_scaling/first_attention_cpu_audit_20261015.json
```

The script verifies the binding and result hashes; every declared runtime, source, manifest and output file; raw BF16 tensor shape/dtype/length/finiteness; source block parameter hash reconstructed directly from HF rows; exact case IDs and little-endian ID hashes; whole-source FIT/DEV split and disjoint group keys; common-prefix query mask; and producer PID/creation and watchdog completion receipts. It rejects unlisted output files other than the final result and completion marker. Runtime source/code/protocol Git blob IDs are independently recomputed from file bytes, without requiring the current repository HEAD to remain at the frozen commit. Owned-process and source parameter identity/version records remain producer witnesses; the raw source parameter byte hash is independently reconstructed.

For each trace, the auditor requires branch shape `[length,2880]`, finite values, and the declared BF16 or F32 dtype. It checks the packed probability layout exactly: query order; 64 query heads; legal keys `max(0,q-127)..q`; one final sink; no masked-key placeholders. Every row is finite, nonnegative, and sums to one within `0.016` for BF16 source or `0.0002` for F32 traces. It computes branch squared error and reference norms in F64, normalizes only metric copies of probability rows in F64, then independently derives pooled relative L2, unweighted sequence p95, rowwise sink-inclusive TV mean/p95, all-token diagnostics and bias-removed diagnostics. P95 uses index `ceil(0.95n)-1` after ascending sort. Saved metric comparisons allow `2e-5 + 2e-4×abs(recomputed)` for F32 versus F64 reduction differences; this tolerance is fixed before viewing outcomes. The four variable-query gates are decided from **recomputed** FIT and DEV metrics and saved in the independent report. Any disagreement with the receipt's gate classification is fatal, including a tolerance-sized difference across a threshold. A failing precision control must correspond to `INCONCLUSIVE_PRECISION_FLOOR` with no candidate/factor requirement. If a candidate is present, all final traces, four gate decisions, final factors, coefficient count, 512-step ledger, factor/ledger file hashes and final Adam/gradient records are checked.

An optional `--replay` runs only when rank factors exist. It independently rebuilds F32 embedding-to-branch arithmetic with source RMS norm, Q/K/V, YaRN rotation, sliding-window-128 plus sink softmax, and O, then repeats with final Q/O rank-256 factors on all 36 cases. Each rebuilt branch must match its stored F32 trace at relative L2 `≤3e-4`; every stored legal-key/sink probability must match at maximum absolute error `≤5e-4`. This CPU replay is computationally heavier and is unnecessary to classify an initial precision-floor stop. It does not attempt BF16 GPU kernel parity, reproduce Adam updates, or claim full-model/chat/physical-Q4 quality.

The auditor caps itself at six CPU threads, checks a 6-GiB RSS and one-hour deadline during each case, and emits at most a 2-MiB JSON report. It records actual thread settings, empty CUDA visibility, RSS and Windows peak working set. Its own code/protocol, manifest, binding and producer-result hashes are compared before and after, and all input/output seals are rechecked at the end. Expected default metric audit: roughly 2–10 minutes and under 3 GiB RAM, depending on source pin hashing and disk speed. Optional full replay: roughly 10–45 minutes and under 6 GiB RAM on a six-core desktop, subject to its one-hour bound. These are planning estimates, not measurements; a single blocking CPU kernel may exceed the in-process deadline before the next check. The producer output remains read-only. A PASS verifies saved evidence and arithmetic under these limits; it cannot independently prove the producer's intermediate optimizer state, exact GPU execution, or any later-block behavior.

## Preserved completed run with cleanup failure

One completed producer run has status `FAILED_GPU_RELEASE`: the final receipt reports 67,108,864 allocated and reserved GPU bytes after garbage collection and `empty_cache`. The auditor may classify its **saved numerical evidence** only under this exact failure class. It requires `gpu_released_before_posthash=false`, positive allocated bytes, reserved bytes at least allocated bytes, post-binding match, unchanged reconstructed source hash, a completed watchdog, and the owned PID/create-time no longer live. It also requires all 108 source/F32/candidate traces, all final and initial factors, a complete 512-step ledger, final Adam state and gradients, and the same independent trace/metric/binding checks as a normal completed numerical run. Missing evidence or a live owned worker is fatal.

For this cleanup-failure branch, recomputed FIT and DEV precision controls must pass, while the recomputed rank-256 gates must fail and agree with the recorded numerical metrics within the already fixed tolerances. The report then says `PASS_NUMERICAL_REJECTION_PRODUCER_FAILED`, retains `producer_status=FAILED_GPU_RELEASE`, and records the independent numerical conclusion `RANK256_F32_REJECT` with `admitted=false`. It does **not** turn the producer run into a PASS or qualify a CPU architecture. The 64-MiB residual may be a runtime workspace, but its cause is unproven by these receipts. The producer files, code, protocol and GPU run remain untouched.
