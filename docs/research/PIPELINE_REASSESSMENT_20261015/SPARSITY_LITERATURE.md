# Sparse donor transfer: evidence and decision

15 October 2026. Scope: pretrained chatbot to a compact CPU C core with useful conditional capacity. This is literature triage and an experiment specification, **not** a conversion result or an admitted runtime. Primary observations were recorded first in [sparsity_evidence.jsonl](sparsity_evidence.jsonl). Local facts below come from the existing [research index](../NATIVE_EXPERT_SCALING_20260925/INDEX.md), [prior evidence](../NATIVE_EXPERT_SCALING_20260925/PRIOR_EVIDENCE.md), and [FFN oracle result](../NATIVE_EXPERT_SCALING_20260925/FFN_REMAINDER_ORACLE_RESULT_20261013.md).

## Decision

Prioritize a **donor-preserving, structured FFN split with learned IDs *and* unnormalized contribution masses**, trained and evaluated in the complete 24-block chatbot before considering extra experts. Split each donor FFN along its intermediate dimension into non-overlapping shards; store each source weight once. At full selection and mass 1, this is a mechanically checkable reordering of the donor FFN. Gradually learn sparse selection and masses under output/logit supervision, charging the router and actual selected source bytes. Keep a shared always-on subset only if it earns its active-byte cost, and use the same total active-byte cap when comparing it with all-routed shards. This takes donor knowledge as the initial function and seeks a causal route to low active cost. **It does not initially create any distinct capacity beyond the donor:** later private experts must contain changed weights and demonstrate incremental held-out benefit at fixed active work.

The first gating question is whether such a sparse FFN can retain *whole chatbot* quality with a cheap router. The second, equally important gate is whether the unchanged attention, readout, state, and contextual generation already consume the 20 ms/token budget. Existing 23-block BF contextual generator measurements are about 50 ms per resident pass, and one I4 generator/readout partial group is over 20 ms. These are actual measured configurations, not universal lower bounds; they make FFN-only success insufficient. A candidate that preserves the donor but retains those organs at their measured cost is rejected for the >=50 useful accepted batch-1 tokens/s goal. No static or dynamic oracle result is a deployed rate.

## Consequences for the local evidence

The source FFN at all 24 Falcon blocks has hidden width 2048 and intermediate width 4608. Its exact per-token remainder-ranking diagnostic reached local-error thresholds with tested active neuron counts 512/2048/32 at sites 0/12/23, respectively. Ranking required all source neuron functions first and is neither a cheap predictor nor an optimal lower bound. Failed source-input sketches and fixed subsets mean re-running the same supervised top-k predictor is low value. Instead, the next variable is a **jointly trained router and masses attached to an exactly initialized donor partition**, with full-model loss and a measured active-byte penalty. Learned masses matter because a selected set can have the right IDs while mis-scaling the residual; granular upcycling explicitly reports this failure. At initialization choose every shard and mass 1, with no softmax sum-to-one attenuation. During sparsification, allow masses to change but constrain their numeric range and test whether their representational effect survives native quantization.

The depth-3/6/12 identity schedules failed quality, so a smaller core cannot be obtained by unchanged layer omission. The D512/L12/E72/top-8 student reached new-FIT KL .70 after 512 replay updates but new-DEV KL 7.11. That indicates a finite coverage/generalization gap for that learner, not a theorem against joint adaptation. It argues for preserving donor operators during the first sparse transfer test and withholding new DEV/RESERVED from training and checkpoint choice. The distinct source capture now running should finish and pass its audit before another learner trial; no concurrent GPU learner is warranted.

**Rate arithmetic is a hard screen.** At >=50 accepted tokens/s, all sequential inference work and sampling/acceptance together must fit within 20 ms per accepted token. For any proposed path, charge `core + router IDs + router masses + selected expert loads + selected expert math + readout + state + sampling + rejected/extra tokens`. Count actual packed bytes read by each selected block, not merely the logical number of neurons or total stored parameters. A shared path is always charged; private bank size can grow while active cost stays fixed only if selector cost, page access, metadata, and misses remain bounded in measurements. This is a design criterion, not an asserted bandwidth estimate.

## Falsifiable next experiment, in order

1. **CPU-only preparation from already captured FIT source fields (no live-capture interference):** choose contiguous intermediate shards with a literal all-shard reconstruction and source numeric identity check. Record per-shard output vectors and source-input features. Fit a *small* router predicting each shard's continuous output contribution and independent nonnegative mass, not merely an oracle ID label. Use a deterministic FIT split, keep the newly captured DEV sealed until architecture and thresholds are frozen. Compare fixed shared subset, all-routed, and one shared-plus-routed variant at identical actual selected-byte budgets. Stop if exact all-shard reconstruction fails or the learned route cannot clear held-out local-error gates with its own measured selection/mass cost. This is a cheap discriminator, not an admission.
2. **Joint quality trial only if step 1 passes:** use the completed source capture, freeze a full-model donor-equivalent starting point, then anneal the per-token selected-byte cap while training router, masses, and bounded adapter weights. Keep all 24 blocks at first; add compact-core surgery only as a separately identified variable after the FFN path has a working whole-model quality result. Measure donor-relative held-out KL, disagreement, generated task behavior, and both IDs and masses on the model's *own* histories. Stop if new DEV fails the predeclared gate or if active donor attention/core timing alone exceeds the remaining 20 ms budget under the chosen encoding.
3. **Same-artifact CPU C check before any capacity claim:** export the trained sparse artifact with packed selected coefficient blocks and run batch-1 end-to-end quality and accepted-token rate on Ryzen 5 3600X/80 GiB. Record median/tail latency, physical DRAM bytes, router bytes/time, per-expert selected bytes, context length, and distinct versus duplicate parameter bytes. Test a new private expert bank only after baseline transfer passes; require held-out gain at unchanged active-byte budget and source-independent data coverage. Stop if >=50 useful accepted tokens/s and the quality gate cannot hold together.

For other 10B/100B families, first classify activation function, FFN partition algebra, residual/attention structure, tokenizer, and whether all-shard reconstruction is exact under the available source representation. ReLU activation sparsity evidence is strongest; SiLU/SwiGLU omit nonzero terms and need explicit output-error testing. Full BF16 100B weights alone are about 200 GB, beyond 80 GiB RAM; even 4-bit packed weights are about 50 GB before scales, metadata, runtime and conversion state. These are dimensional estimates, not feasibility or speed results. Streamed layerwise conversion may avoid simultaneous full weights, but gradient/optimizer state for end-to-end upcycling is much larger; S02's 110B/1T-token regimes and S07's 100B-2T-token regimes make that route economically remote on one RTX 3060 12 GiB. The near-term claim should be limited to a tractable donor and then tested on a second family with the same admission process.
