# GPT-OSS-120B first attention Q/O rank-256 falsifier

**Status:** code prepared; no tensor acquisition, GPU run, training, compilation, or quality claim in this step. This experiment tests only the actual-weight first attention block of the pinned [GPT-OSS-120B config](https://huggingface.co/openai/gpt-oss-120b/blob/b5c939de8f754692c1647ca79fbf85e8c1e70f8a/config.json) and [official reference implementation](https://github.com/openai/gpt-oss/blob/5681a6b6552635e7b29cde94a61ca6a7aee90ebd/gpt_oss/torch/model.py). It says nothing directly about chat quality, downstream blocks, full-model CPU timing, or the 120B conditional expert store.

## Source and corpus contract

The separate acquisition step supplies `results/native_expert_scaling/first_attention_source_20261015/manifest.json` with schema `FIRST_ATTENTION_SOURCE_V1`. The code requires the exact pinned official config and reference files in `large_family_metadata`, their recorded byte counts and SHA-256, and exactly ten layer-zero HF tensors: input RMS scale; Q/K/V/O weights and biases; and attention sinks. Tensor descriptors carry the exact HF name, raw contiguous BF16 file path, shape, dtype, byte count, SHA-256, source shard and source offset. Shape requirements are enforced before any GPU work. Separate raw BF16 embedding rows `[U,2880]` are indexed by sorted token IDs. This is a selected first-block slice, with no experts, later blocks or vocabulary head.

The manifest contains 36 tokenized cases: 24 FIT (three original FIT cases in each of eight sources) and 12 DEV (three original DEV cases in each of four entirely disjoint sources). The DEV sources are fixed by SHA-256 of `first-attention-source-holdout-v1:` plus source name, yielding `smol-magpie-ultra`, `metamathqa-50k`, `smol-constraints`, and `self-oss-instruct`. The acquisition step excludes cross-cohort first-user and group aliases before sorted-ID selection and records its filter. The fitter enforces disjoint source domains, `group_key` and `first_user_key`. Each case stores the full `canonical_input_ids` and its hash, the first at-most-256 raw `input_ids` and their `used_ids_sha256`, original length, unchanged source `prefix_sha256`, source messages and corpus pins. The fitter checks both hashes against little-endian contiguous unsigned-32-bit IDs and checks that capped IDs are exactly the canonical prefix. `prefix_sha256` keeps the adopted source-message-prefix convention. It also hashes every `input_pins` and `tokenizer_files` path plus the acquired selection/eligibility plans before and after. The run maps each capped ID to an authentic downloaded BF16 embedding row and never reads Falcon IDs/logits, RESERVED labels, or a long-case selection. This is a whole-source local holdout over the selected 12 domains, not a claim about every possible source.

## Numerical control and candidate

At runtime the code extracts only `ModelConfig`, `RMSNorm`, `RotaryEmbedding`, `_apply_rotary_emb`, `sdpa`, and `AttentionBlock` AST nodes from the hashed official reference. It checks the reference defaults against the pinned HF configuration, including YaRN factor, beta fields and layer-zero sliding attention. It instantiates the official first block and combines separate HF Q/K/V rows into the official QKV order. It checks all imported values finite and copies genuine BF16 source weights, including norm, all biases and sink logits. The reference path applies source RMS norm, Q/K/V, YaRN RoPE, causal sliding-window-128 mask, sink-aware softmax, O and residual. A temporary hook captures the official pre-O context and pre-residual O branch. The manual sink-inclusive probability path must reproduce both captured BF16 tensors exactly, and the captured branch must reproduce the official residual exactly, before fitting. The captured official branch is the teacher target; a parameter-byte hash before and after guards frozen source identity. A full-rank F32 source path with the same weights provides a precision control against actual BF16 source branch/probabilities. The manifest seals `common_prefix_length`, the maximum shared leading token span across all 36 canonical cases; every case must contain at least one later query. FIT loss and all gates use query positions at or beyond that length, so a common Harmony prefix cannot dominate. All-token metrics remain diagnostics from the same complete traces. The BF16-versus-F32 precision control must pass **the same four gates separately in FIT and DEV**, including sequence p95, or the result is **INCONCLUSIVE_PRECISION_FLOOR**, with no rank fit or quantized claim.

Only Q and O are compressed. K, V, input RMS norm, biases, sinks, RoPE, sliding mask and residual semantics remain source-fixed. Q is `[4096,256]×[256,2880]`; O is `[2880,256]×[256,4096]`: exactly 3,571,712 fitted coefficients. FIT-only normalized embedding states form a covariance-damped (`λ = 1e-4 × mean diagonal`) whitened SVD of the actual Q matrix. FIT contexts produced by that compressed Q and fixed source K/V support a damped least-squares O target to the genuine FIT source attention branch; its weighted rank-256 SVD initializes O. This initializer uses no DEV examples.

The fixed training schedule is seed `20261015`, 512 Adam updates, learning rate `1e-3`, one FIT sequence per step in sorted cyclic order, and loss `variable-query branch relative MSE + 1.0×mean sink-inclusive TV`. Source BF16 probabilities are copied to F32 and renormalized for TV calculation only; the authentic stored BF16 probabilities remain untouched. Only four factor tensors receive gradients. The first two updates are a GPU allocation/reservation probe; exceeding 8 GiB allocated or 9 GiB reserved aborts before the remaining 510. No DEV-based checkpoint selection, alternative seed, rank search or step extension is permitted. Rank 512 is not fitted or used for promotion by this implementation; it would be a separate diagnostic if later authorized.

## Gates, artifacts and bounds

FIT and DEV are both reported, but the F32 rank-256 local gate requires on **each** split's variable-query positions: pooled pre-residual branch L2 ≤1%, unweighted sequencewise relative-L2 p95 ≤5%, sink-inclusive TV mean ≤.01 and rowwise TV p95 ≤.05. TV rows are every (query token, attention head), including the sink probability as the final category; p95 is the higher nearest-rank value at index `ceil(.95×n)-1`. All-token diagnostics, per-case metrics, worst sequence and worst TV row are retained. If FIT fails, the rank-256 recipe is rejected regardless of DEV; DEV remains a fixed diagnostic. If both pass, status is only `RANK256_F32_GATE_PASS_PHYSICAL_Q4_PENDING`. It cannot promote a CPU architecture until a separately qualified physical Q4_K factor encoder/kernel and end-to-end engine are tested. No Q4 encoder is improvised here.

The output directory is exclusive. It retains source BF16, full-rank F32 and final candidate branch/probability traces for all 36 cases, initial and final F32 factors, final Adam state and last gradients, and a **flushed, fsynced per-update ledger** with case/loss/component/gradient/parameter-hash/resource records. This is a producer witness; an independent replay is still required for proof. Probability traces are losslessly packed from the complete causal sliding-window distribution: query-major, then eight KV heads × eight query heads, then legal keys oldest-to-newest followed by the sink. No masked zeros are stored; the query length/window rule reconstructs them. The original BF16 source values remain BF16. Per-split and per-case metrics, owned PID/create-time records written before GPU work, runtime/source/manifest SHA-256 pins, frozen Git blob hashes and before/after binding seals are retained. An unrelated later HEAD movement does not break a sealed byte/blob binding. These traces plus the manifest and F32 factors allow a future independent CPU auditor to replay all 36 candidate cases without repeating a source GPU pass. `CUBLAS_WORKSPACE_CONFIG=:4096:8`, visible GPU 0, no TF32 and six CPU threads are fixed before work. A separate watchdog process can terminate an uninterruptible worker at the 2.5-hour wall, 8-GiB RSS or 2-GiB output caps; in-process checks enforce <8 GiB allocated and <9 GiB reserved GPU memory and the 2-hour GPU deadline. Failure leaves the owned-process and watchdog/partial-update receipts. The first two updates record a resource/time projection; if 512 updates project at least one hour, work stops for review rather than silently continuing.

## Enforced runtime boundary

The lightweight watchdog starts without importing PyTorch, confirms readiness
before GPU work, and binds the worker PID/creation time. It enforces the wall,
GPU-phase wall, combined-RSS and output caps even inside blocking numerical
calls. The worker applies the PyTorch allocator fraction cap, checks allocated/
reserved peaks at every stage/update, requires the watchdog to stay live, and
releases GPU tensors before final input hashes. CUDA deterministic algorithms
and fixed cuBLAS workspace settings are enabled before numeric work.

Input seals include the PyTorch CPU/CUDA/Python and c10 runtime DLLs, alongside
the declared source modules and exact data descriptors. Source parameter values,
identities and version counters are witnessed before/after. Identity/version
and optimizer execution records remain producer witnesses until independently
replayed; they do not replace the later CPU trace/metric audit. JSON control
markers publish by exclusive Windows rename to avoid partial reads. No
recovery may overwrite an existing result directory or change the fixed steps.
