# Activation-aware generator/readout calibration: artifact feasibility (15 October 2026)

This is a feasibility map, not a completed conversion or authorization to launch a new run while the distinct-source GPU capture is live. The new variable relative to the tested codec is **FIT-activation-weighted, output-aware adjustment of low-bit codes and scales, with sequential native-state composition**. The 14 October codec was explicitly weight-only: row max/RNE I8 or group-128 I4, with *no calibration or weight fit* (`../NATIVE_EXPERT_SCALING_20260925/CONTEXTUAL_GENERATOR_CODEC_PROTOCOL_20261014.md:9-23`). Its I4 source-field worst error is 15.283569% and its three-worker generator-only median is 22.80625/23.84020 ms (`CONTEXTUAL_GENERATOR_CODEC_RESULT_20261014.md:7-32`). A better fit is meaningful only if decoded-value correctness, actual source-field gates, evolving-state quality and joined cost are separately proven.

The existing shadow bridge already preserves all original 24 attention/FFN/head operations while replacing each mixer with a native row/state/readout call. Its `NativeBridge.mix` computes later-layer `h`, calls original `mixer.in_proj(h)*mup_vector`, then passes BF16 fields and site-specific `q/scale` to `row_state` (`benchmarks/native_expert_scaling/full_width_native_chat.py:217-220,237-281`). A future candidate can change exactly the field producer and readout parameter pointers there, leaving original attention/FFN/LM head and source hidden width 2048 in place. This is a GPU-assisted *quality bridge*, not a CPU engine or rate result (`FULL_WIDTH_NATIVE_CHAT_RESULT_20261013.md:5-13,59-76`). It must be a newly bound/audited artifact, not an asserted inheritance of the current bridge's numerical gates.

## Historical boundary: what is already tried

The current contextual I8/I4 attempt is uniform scale plus nearest-even, with exact decoded-weight and C output audits but no activation-aware optimization or own-history substitution (`CONTEXTUAL_GENERATOR_CODEC_PROTOCOL_20261014.md:15-20,34-54`; `CONTEXTUAL_GENERATOR_CODEC_RESULT_20261014.md:13-26`). The p6 readout uses row-max/RNE codes and later exact I16 input/dot execution; its six ternary planes are a *reconstructible representation*, while the physical fast kernel reads int16 weights (`TERNARY_READOUT_PRECISION_RESULT_20261013.md:21-26`; `INTEGER_READOUT_RESULT_20261013.md:13-28,139-146`). Exact F64 trit LUT was about 4.2–4.6× slower than dense and the exact byte LUT 8.50–9.10× slower than I16, so recoding the same q into tables is a tested cost failure (`TERNARY_READOUT_NATIVE_RESULT_20261013.md:47-80`; `EXACT_INTEGER_LUT_RESULT_20261013.md:65-84,126-127`). A new readout bit-depth proposal requires a different *physical* kernel and a cost proof, not a relabeling of p6.

GPTQ is **not historically untried in this repository**: `benchmarks/donor_adaptation/ternary/t2_rules.py:r4_gptq` and the E20 Qwen head/FFN study compare activation-aware scales and compensated ternary rounding. That result is donor/organ/format specific and did not calibrate Falcon's 23 `G` matrices jointly with its 24 native `O` projections; see `docs/research/donor_adaptation/probes/E20_RULE_OR_FORMAT.md:50-76`. Synthetic additive-codebook/LUT experiments explicitly used synthetic values and no learned codebooks or pretrained quality (`benchmarks/native_expert_scaling/meth408_ling_additive_cost.py:173`, `meth410_ling_static_pair_lut.py:195`). A search of the native Falcon result and converter files found no completed Hessian-aware/GPTQ or learned-additive-codebook artifact for these actual `G`+`O` matrices. Do not frame the pilot as a first-ever GPTQ test across the repository.

## Minimum experiment that could change the decision

Start at site 12, the middle representative layer, with **no new source model run**. Bind the exact existing 48 original FIT/DEV IDs and full-width candidate traces, canonical `G`/`O` hashes and frozen runtime. FIT only: hold the actual I4-g128 storage geometry and charged decode path fixed, compare prior max/RNE against one predeclared activation-weighted compensation method (for example a damped `HᵀH` row/group reconstruction with fixed group128 and scale policy). Use FIT candidate `h` and original BF field targets; report gate/x/B/C/dt slice error, not merely weight MSE. Separately compare the qualified p6/I16 `O` control against a prospectively specified low-bit `O` candidate if a compiled low-bit kernel is available. A p6-code adjustment can diagnose compensation but does **not** lower its physical I16 cost.

For a genuinely **joint** `G+O` claim, sequentially replay the quantized site-12 generator into its own native state on the same FIT histories, capture the resulting normalized 3072-vector before the readout, then fit/compare readout codes against the original site output. Re-evaluate on untouched DEV with no selection or refit. The replay mechanism can be adapted from `native_24_cost.record_rows` and the qualified `row_state` ABI; the needed *changed-state normalized activation archive does not yet exist*. One local pass should stop if the I4 generator cannot meet the original 1% source-field screen or if a candidate readout cannot meet the prior local readout gates, because a 24-layer whole model would then have no admitted local basis. If both pass, freeze a new 24-site bridge with all original attention/FFN/head intact and require original whole quality/task/followup controls, then measure the exact joined CPU active time before a larger calibration campaign. The existing I4 generator+I16-readout partial already takes 24.125/22.442 ms median under tested active waiting, before other organs (`ENCODED_ORGANS_WAIT_RESULT_20261014.md:15-28`); numerical recovery alone is insufficient.

Cost boundary: source `G` has 315,785,216 coefficients across 23 sites; dense full 2048×2048 second-moment storage is about 32 MiB in F64 **per distinct activation distribution**, and a naive full dense solve per row/site is much larger than the old one-pass RTN conversion. A site-12 groupwise/pinned-data pilot is tractable in memory; the complete 24-site fit/benchmark, new low-bit `O` kernel, and own-history bridge are substantive new implementation and GPU/CPU work. None is present as a finished, unintegrated artifact. Preserve FIT/DEV split boundaries and the live capture's new packets until their separate adoption audit; do not use new DEV for fitting or checkpoint choice.
