## Exact metric definition

Start each document with an empty KV cache. Tokenize the text with the source checkpoint's `tokenizer.json`, without automatic special-token insertion; require the same ID sequence on BF16 and Q4, exact text round-trip, and no special IDs in the payload. The initial marker is `<s>`/BOS ID 1: the published GGUFs declare `bos_token_id=1`, `add_bos_token=true`, and the source post-processor adds `<s>`. Do not append EOS to the payload or include markers or chat prompts in the byte count.

**Pre-score addendum, VOID_APPARATUS tokenizer (September 18):** the first Q4 instrument attempt was rejected before any forward pass/score: on the first document, the source Python tokenizer produces 2034 IDs versus 2291 from `llama_tokenize(..., add_special=false, parse_special=false)`, with the first divergence at position 1 (`14084` versus `65`). A second attempt only made the diagnostic visible and produced no score. The GGUF header reports `tokenizer.ggml.pre=gigachat`, but `llama-vocab.cpp` at the pinned commit `5b335f4` maps it to `LLAMA_VOCAB_PRE_TYPE_GPT2`; the GPT-2 regex in that switch differs from the source `tokenizer.json` `Split` regex. This is a source-level explanation of the mismatch, not a quality measurement. A metadata-only read of the Q4 GGUF also compared all **128.000** `model.vocab` entries and the **15** source JSON `added_tokens` by ID: **zero mismatches** with `tokenizer.ggml.tokens` (128.256 positions total). The BF16 and Q4 GGUFs have byte-identical tokenizer fields in the earlier header audit. Thus the ID→token mapping is preserved, even though `llama.cpp` text→ID conversion is not.

For this likelihood test, pass source-tokenizer IDs to the model, verifying **before every run** the complete source→GGUF mapping for all defined entries and recording counts/hashes/outcome in the manifest. Record `llama_tokenize` divergence per document, but do not use it to construct inputs. This is an apparatus change made before any BPB observation, not a post-hoc gate exception. Reject the run if even one ID mapping differs or byte round-trip fails. The earlier `llama.cpp` CLI generation does not prove tokenizer fidelity to the source; a final deployment must use the source tokenizer or repair and demonstrate text→ID parity in the C engine. This corrected BF16–Q4 GGUF comparison remains preliminary and does not by itself prove that the entire BF16 GGUF is faithful to the safetensors checkpoint.

Given payload `t_0 … t_(n−1)`, model input is `BOS, t_0 … t_(n−2)`: logits at position `i` assign probability to `t_i`. Sum `logsumexp(logits_i) − logits_i[t_i]` in float64, computed from the runtime's float32 logits; convert to bits by dividing by `ln 2`. `BPB = Σ bits / Σ len(text.encode('utf-8'))`. Exclude any truncated document, non-finite logit, token mismatch, or missing score; do not silently replace it. Persist per document: `source_document_id`, `category`, `tokens`, `bytes`, `bits`, and a separate manifest with model, tokenizer, and corpus SHAs; revision/runtime; parameters; timings; and selection rules. Do not save text in score logs.

For the instrument test, explicitly check off-by-one behavior on a synthetic sequence with known probabilities and, on a short real document, compare single prefill with causal chunking. Parity may have a declared numerical tolerance, but systematic misalignment invalidates the comparison. The end-to-end speed benchmark is a separate experiment: full-logit scorer time is not generation tok/s, and `llama.cpp` throughput is not C-engine throughput.

## Decisions this test does not authorize

Even ΔBPB Q4−BF16 ≤+0,02 on the full corpus is insufficient to declare success: a pristine heldout, tasks/rollout, proof of complete identity relative to the source checkpoint, and an artifact actually running at ≥50 tok/s in the C engine are still missing. Conversely, a clear failure of Q4 fidelity in the published format is informative for that path, but does not rule out Q6/Q8, QAT, or a different donor; each would require a newly justified cell and its own budget.
