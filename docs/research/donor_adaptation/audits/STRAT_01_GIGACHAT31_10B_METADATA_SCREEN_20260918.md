# STRAT-01 — GigaChat 3.1 Lightning 10B-A1.8B: metadata screen

**September 18, 2026. Primary sources, headers, hash comparison, and extracted MTP sidecar.** No complete source-checkpoint shard was downloaded and no model was loaded; no kernel, local task, T4, C port, or CPU throughput. The hash comparison streamed ~1,576 GB of payload from the four tensors without persisting it to disk; subsequently, only the ~1,614 GB MTP sidecar was saved. Decision: donor is licensed and producer-evaluated, **but not promoted to a port/heavy benchmark**: active geometry and the MTP mechanism require a separate batch-1 feasibility test on the target CPU.

## Model structure and traffic threshold

The BF16 config declares `DeepseekV3ForCausalLM`, hidden size 1536, 26 base layers, 64 routed experts with top-4, one shared expert, `moe_intermediate_size=1280`, a dense first layer, MLA, an untied head with vocab 128.256, and one MTP layer (`num_nextn_predict_layers=1`). The [Transformers v4.57.3 implementation](https://github.com/huggingface/transformers/blob/v4.57.3/src/transformers/models/deepseek_v3/modeling_deepseek_v3.py) fixes the MLA, MoE, and MLP projection dimensions used below. The pinned index counts 5.323 tensor keys, layers `0..26`: layer `26` has its own `shared_head.head` projection and `embed_tokens`, and is accounted for **separately**, not as a free base layer. The card describes about **1,8B active parameters/token**, but does not provide a tensor-by-tensor definition here for the head/MTP.

| Base component per one autoregressive token | Formula from config + operators | Large active weights |
|---|---|---:|
| MLA Q/KV/O, 26 layers | `26×[1536×(32×192) + 1536×(512+64) + 512×32×(128+192) + (32×192)×1536]` | 650.051.584 |
| Routed experts, layers 1–25 | `25×4×3×1536×1280` | 589.824.000 |
| Shared experts, layers 1–25 | `25×3×1536×1280` | 147.456.000 |
| Dense MLP, layer 0 | `3×1536×8960` | 41.287.680 |
| Router, layers 1–25 | `25×1536×64` | 2.457.600 |
| Main untied head | `1536×128256` | 197.001.216 |
| **Total large base components** | | **1.628.078.080** |

The base ledger was **reconciled against the shapes of all 5.323 keys** by reading only the safetensors headers of the six shards (`model-00000`..`model-00005`), using HTTP `Range` requests against an immutable revision: headers of 103.400, 125.856, 126.672, 126.872, 126.872, and 50.408 bytes. The sum of shapes is exactly **11.479.750.784 elements**, matching the API and index. For the 25 MoE layers, exactly four experts with identical per-token shape were counted, not all 64. The first mechanical calculation erroneously included `shared_experts` matrices under `dense` as well; the classifier was corrected, and the final sum matches the independent formula in the table. No inference was performed on weight values or actual routing.

The base sum excludes norm, bias, indexed input embedding, KV/state, quantization scales, and **the entire cost of MTP layer 26**. It is operator-shape accounting, not a trace of bytes read. The pure-payload W4 for the base as defined is **814.039.040 B/token**, or **40,70 GB/s at 50 tok/s**; under the 14 ms project budget it requires **58,15 GB/s** for these matrices alone. Even this tighter estimate exceeds the older E30 reference of 36,30 GB/s, which is not a universal bound for every kernel, reuse pattern, or layout.

## MTP layer and acceptance threshold (idealized model only)

The effective shapes of layer `model.layers.26` include a second full head, `shared_head.head.weight [128256,1536]`, and a second table, `embed_tokens.weight [128256,1536]` (the latter is indexed, not read in full for each draft). The **large active-matrix cost per MTP draft**, reconstructed from the shapes, is:

| MTP component | Elements |
|---|---:|
| MLA Q/KV/O | 25.001.984 |
| Four routed experts | 23.592.960 |
| Shared expert | 5.898.240 |
| Router | 98.304 |
| `eh_proj` | 4.718.592 |
| Separate MTP head | 197.001.216 |
| **Total large MTP components** | **256.311.296** |

At hypothetical uniform W4, this is **128.155.648 B/draft**; base+MTP would read **942.194.688 B/cycle** if each large matrix were loaded only once. This is not a measurement and excludes the cost of verifying two positions, scales, cache, or irregular accesses. For one top-1 proposal per cycle, if `p` is the acceptance probability and a cycle ideally produces `1+p` tokens, the 36,30 GB/s E30 reference would require **`p≥0,298`** merely to fit 50 accepted tokens/s within the full 20 ms, or **`p≥0,854`** to meet the 14 ms/accepted-token project budget reserved for streaming. These are **necessary conditions under favorable assumptions**, not sufficient conditions or acceptance predictions. Without MTP, the 814,04 MB base alone would require at least 22,43 ms at the same bandwidth reference, before compute. The published H100 report does not measure `p` batch-1 on our CPU.

Using the card's **nominal** 1,8B active-parameter count instead, W4 would be 0,90 GB/token and 45 GB/s at 50 tok/s; W2 would be 0,45 GB/token and 22,5 GB/s. These values are a separate scenario and must not be added to the base ledger. Do not treat W2 as quality-valid: the W2 PTQ tested on StdMoE failed, but does not determine the outcome for this different checkpoint.

MTP **does not give two tokens for the cost of one**: the draft, its additional head, and verification all have a cost, and only actually accepted tokens count without changing the target distribution. The card reports BF16 at **1×H100 SXM5, vLLM, concurrency 32**: 2.866 output tok/s without MTP and 3.346 with MTP, +16,7% in that setting. This is not a CPU batch-1 test or an acceptance/throughput prediction for our architecture. Naively applied to the shape-only base-W4 estimate, a factor of 1,167 would not suffice to turn 40,70 GB/s into 36,30 GB/s, **even ignoring the cost of the MTP layer**; this arithmetic does not adjudicate MTP on CPU because cost/reuse/acceptance can differ.

## The published GGUF does not contain MTP

The producer's [GGUF repository](https://huggingface.co/ai-sage/GigaChat3.1-10B-A1.8B-GGUF), revision [`97045b260251cfa86f5ad25638fa2dd074153446`](https://huggingface.co/ai-sage/GigaChat3.1-10B-A1.8B-GGUF/tree/97045b260251cfa86f5ad25638fa2dd074153446), publishes BF16, Q4_K_M, Q6_K, and Q8_0. The [API tree](https://huggingface.co/api/models/ai-sage/GigaChat3.1-10B-A1.8B-GGUF/tree/97045b260251cfa86f5ad25638fa2dd074153446?recursive=true) reports Q4_K_M at **6.474.702.976 bytes** (blob SHA-256 `68a8732fb5cee04f83ebffd7924e15c534d4442c5a43d2ba9e2041fe310b8deb`) and BF16 GGUF at **21.356.281.984 bytes** (blob `e7a6409be0ac197babf21c48cfc8a96486d035c1e7a784feadd817b7b883c08e`). File size is **not** equivalent to bytes read per token.

I inspected the GGUF v3 headers via HTTP `Range`: BF16 and Q4_K_M both have 47 metadata keys, **414 tensors**, `deepseek2.block_count=26`, `general.architecture=deepseek2`, and no `blk.26`, `mtp`, or `draft` name. The headers end at byte 6.102.892 in both files. For convenience, the requested range was `0..8.388.607`: it therefore also transferred **2.285.716 initial payload bytes per file** beyond the header, which were neither decoded nor used. Q4_K_M is thus a **base-only artifact**: it cannot provide the safetensors checkpoint's MTP draft, even though the general card mentions MTP. Do not use a Q4 GGUF test as evidence for the speculative path. This Q4's BPB fidelity to the same BF16 is not reported here, and conversion binding to the BF16 SHA is not established by the headers alone.

## Experimental disposition

### MTP path verification (September 18, after the GGUF screen)

The [`llama.cpp` converter at revision `542348a35c9ed5a3f3b554cac1191ee3d3df8173`](https://github.com/ggml-org/llama.cpp/blob/542348a35c9ed5a3f3b554cac1191ee3d3df8173/conversion/deepseek.py) registers `DeepseekV3ForCausalLM` in the `DeepseekV2Model` class with `skip_mtp=True` and an explicit comment that MTP support for DeepSeek models is missing. The [CLI at the same revision](https://github.com/ggml-org/llama.cpp/blob/542348a35c9ed5a3f3b554cac1191ee3d3df8173/convert_hf_to_gguf.py) accepts `--mtp` **only** for classes with `supports_mtp_export`; this class does not. Do not confuse this limitation with MTP support implemented for other architectures (for example, DeepSeek V3.2): `--mtp` is rejected for the GigaChat DeepSeek V3 checkpoint; standard conversion omits the layer. This is a reading of pinned source code, **not** an attempted conversion.

The [name search in the Hugging Face catalog](https://huggingface.co/api/models?search=GigaChat3.1-10B-A1.8B&limit=100) and file listings for the producer's GGUF repositories and those of `mradermacher` and `SergeyLizin` did not show a file identified as `mtp`/`draft`. This **does not prove the global absence** of a sidecar (different names or later publications require a new check), nor does it prove that every third-party GGUF is base-only: that would require reading their respective headers. The producer GGUF remains the only one verified tensor-per-tensor here.

The [pinned BF16 safetensors index](https://huggingface.co/ai-sage/GigaChat3.1-10B-A1.8B-bf16/blob/189fff27a1dee68473960c3d5bca53e0e07a3191/model.safetensors.index.json) places **all 210 `model.layers.26.*` keys** in `model-00000-of-00005.safetensors` alone, together with the three root keys `model.norm.weight`, `lm_head.weight`, and `model.embed_tokens.weight`. The [pinned API tree](https://huggingface.co/api/models/ai-sage/GigaChat3.1-10B-A1.8B-bf16/tree/189fff27a1dee68473960c3d5bca53e0e07a3191?recursive=true) gives this shard a size of **4.986.065.392 bytes**, LFS SHA-256 `612f84d11aca544694ef674e58781d0c39ae4b2046f9cadeada79f1d37e581b6`. The `of-00005` naming actually spans shards `00000..00005` (six files), as confirmed by the index: do not infer the file count from the string alone. The MTP-specific head/embedding are already in layer 26 and must not be confused with the three shared root keys.

**Range manifest verified without payload:** the HTTP `206` response for bytes `0..103407` of the pinned shard contains a 103.400-byte safetensors header preceded by an 8-byte length. The 210 MTP keys in the header match the 210 index keys exactly by name (zero set difference; 835 keys in the full header). Sorting their `data_offsets`, the first begins at `2.554.549.504`, the last ends at `4.168.979.840` (offset relative to the start of the payload), and **there are no gaps** between adjacent intervals. Tensor byte sizes sum to exactly **1.614.430.336** = 807.215.168 BF16 elements, including the 60 experts inactive for each token and the draft tables; do not confuse this with the 256.311.296 large weights *active per draft* above. The only file range needed to *extract the 210 tensors* is therefore inclusive `bytes=2554652912-4169083247` (absolute offset = `8+103400+data_offset`), in addition to the 103.408-byte header for metadata and integrity. Requests for **a single byte at each endpoint** returned `206` and a consistent `Content-Range` (the last was `bytes 4169083247-4169083247/4986065392`): the server supports that range, without transferring the full interval. **This is a metadata/contiguity check, not a download or hash of the 1,614 GB of content.** A future extractor must use the complete blob SHA as source identity, verify `206` and `Content-Range`, and check parity of exported tensors; hashing the full blob would require reading it all. The range alone implies no parity with the published base GGUF and no executable draft.

**Exact identity of shareable matrices, verified across all bytes:** full SHA-256 hashes were calculated for the following BF16 tensors from the same shard/revision via four Range requests streamed through RAM (HTTP `206`, with length and `Content-Range` checked). No file was saved.

| Pair, 394.002.432 bytes each | SHA-256 of both members | Outcome |
|---|---|---|
| `lm_head.weight` / `model.layers.26.shared_head.head.weight` | `44e76ffcc70ec1587b815ecf0843c25357b29ed74d4f7d26b0c0c4b9f9e679c0` | identical |
| `model.embed_tokens.weight` / `model.layers.26.embed_tokens.weight` | `f95153ccd83b7d85881f9cdbfb1d3ca7425c59a4ee040b740519926ae951363f` | identical |

Thus, **identity of BF16 values is verified**, not just shape. In a future format, these two pairs could be represented as aliases if tokenizer, precision/scaling, and loader semantics allow: the 210 MTP tensors occupy 1.614.430.336 raw B, but omitting the **two copies** of 394.002.432 B each would reduce the unique payload to **826.425.472 B**; however, a *standalone* 210-key safetensors sidecar cannot omit them without a loader that explicitly resolves aliases. For **traffic per cycle**, the embedding is indexed and the head is the only recoverable large active component: removing its duplicate read of 197.001.216 weights = 98.500.608 B W4 would reduce the ideal base+MTP bound from 942.194.688 to **843.694.080 B/cycle**, *only if* both head logits are computed with a shared weight read. At the E30 reference of 36,30 GB/s, the ideal necessary condition would become `p≥0,162` for 50 accepted tok/s or `p≥0,660` for 14 ms/accepted-token, still **before** scales, compute, KV, verification, and overhead. Weight equality alone does not guarantee that two matvecs at different times avoid two DRAM reads; a weight-once kernel and correct scheduling still need implementation/measurement. These hashes do not demonstrate parity between the published Q4 GGUF head and a quantization of the same BF16.

**Actual sidecar extraction (September 18):** [`strat01_gigachat_mtp_extract.py`](../../../../benchmarks/donor_adaptation/density/strat01_gigachat_mtp_extract.py) uses only the standard library, defaults to a metadata-only plan, and requires explicit `--execute`. Nine [synthetic HTTP Range tests](../../../../benchmarks/donor_adaptation/density/test_strat01_gigachat_mtp_extract.py) pass, including interruption/resumption with per-chunk hashes, partial-file corruption, symlinks, and overwrite prevention. The live plan verified the pinned index/header (`header SHA-256 e970752e3764fc1be2a71b800c96e7d580f2b5763ae772eb453b9b2b386cd67b`), 210 keys, and the range above. With 910.314.672.128 B free at preflight, execution created the local file `benchmarks/donor_adaptation/density/results/strat01_gigachat31_mtp_bf16_189fff27.safetensors`: **1.614.456.643 B**, SHA-256 **`c340ed41c1355441207357723b984fc336082e7c0e8a00deeb6f4fce15c46119`**, 210 tensors; the matching `.manifest.json` records offsets/shapes/dtypes and provenance. `.part` and `.part.resume.json` files are absent after finalization. An independent second hash via `Get-FileHash` matches the manifest, `safetensors.safe_open` reads 210 keys and one BF16 `[1536]` `enorm`; three small tensors (`enorm`, `hnorm`, `shared_head.norm`) compared in full against new HTTP Range requests are byte-identical. **The full 4,986 GB shard** was not read, so its LFS SHA-256 remains a pinned identity not recalculated locally; these checks do not prove complete value parity for all 210 tensors against a second read of the source. The large artifact remains local/unversioned; the code and manifest allow reproduction.

**Next decision:** weight extraction is complete, but the sidecar is not yet an executable draft. The gate is now to pair these weights with a target reference having **consistent hidden state and tokenizer**, verify logits and speculative acceptance on real tokens, and then estimate/port MLA+MoE+MTP to the C engine. Do not use H100 speedup or base-only Q4 as a substitute for that measurement; the file alone does not pass any rate/quality gate. The head/embedding alias variant requires an explicit loader and was not applied to the 210-tensor artifact. Do not automatically download the remaining ~21 GB BF16 or run `convert_hf_to_gguf.py --mtp` as a shortcut.

### Addendum: llama.cpp MTP runtime contract (September 18)

The subsequent reading of `llama.cpp` source at commit [`5b335f413e4f73b0809c4fe39af894efbcc6a0d2`](https://github.com/ggml-org/llama.cpp/tree/5b335f413e4f73b0809c4fe39af894efbcc6a0d2) refines the earlier assessment of the *converter*: the [DeepSeek2 runtime](https://github.com/ggml-org/llama.cpp/blob/5b335f413e4f73b0809c4fe39af894efbcc6a0d2/src/models/deepseek2.cpp) already has `graph_mtp`, detects an `mtp_only` GGUF by the absence of `blk.0.attn_norm.weight`, loads `blk.26.nextn.*`, exposes the post-final-norm hidden state, and can use optional MTP head/embedding tensors or fall back to the root ones. The [tensor map](https://github.com/ggml-org/llama.cpp/blob/5b335f413e4f73b0809c4fe39af894efbcc6a0d2/gguf-py/gguf/tensor_mapping.py) includes the source names `model.layers.{bid}.eh_proj`, `.embed_tokens`, `.enorm`, `.hnorm`, and `.shared_head.*`. This makes a separate draft GGUF a path to investigate, **not** a format already produced from our sidecar.

**Reproducible blocker before any benchmark:** the [pinned BF16 config](https://huggingface.co/ai-sage/GigaChat3.1-10B-A1.8B-bf16/blob/189fff27a1dee68473960c3d5bca53e0e07a3191/config.json) does not define `q_lora_rank`; in the extracted manifest, layer 26 contains `self_attn.q_proj.weight [6144,1536]` and no `q_a_proj`/`q_b_proj`. By contrast, `graph_mtp` in the source above asserts `hparams.n_lora_q > 0`, `layer.wq_a`, and `layer.wq_b`, then uses only that path. For GigaChat Lite, the MTP graph is **not executable as-is**: the direct-Q branch analogous to the one already in the target graph must be implemented and tested, in addition to DeepSeekV3 export support. The [converter at the same revision](https://github.com/ggml-org/llama.cpp/blob/5b335f413e4f73b0809c4fe39af894efbcc6a0d2/conversion/deepseek.py) retains `DeepseekV2Model.skip_mtp=True` and does not enable `--mtp` for `DeepseekV3ForCausalLM`; the DeepSeekV3.2 class cannot be applied by renaming the architecture, because it uses a different contract.

**Distinct root norm, verified byte-for-byte:** a new HTTP `Range` `206` request to the same shard/revision, with exact `Content-Range` and length, read both 3.072 B BF16 tensors. `model.norm.weight` has SHA-256 `12935320d4033c560cec87fc07cc5d3f0f28ef2cb5b0f509d7a2a05246b0e44b`; `model.layers.26.shared_head.norm.weight` has SHA-256 `18c07b9ce3bf4ea01aca84b508657b1495efe730707e25884755cc8fac6a8c8f`, matching its value in the local sidecar. **They are not aliases.** The `mtp_only` loader still requires root `output_norm`, so a faithful standalone export must fetch these 3.072 B; it cannot substitute the MTP norm. The head and embedding, by contrast, were shown above to be byte-identical. The full shard was not downloaded.

The minimal falsifiable sequence is: (1) build an MTP-only converter/manifest with metadata `n_layer_nextn=1`, `blk.26` tensors, and root embedding/head/norm faithful to the same BF16 SHA, with completeness and shape checks; (2) enable the direct-Q case in the MTP graph and compare logits/hidden state against a BF16 reference on fixed inputs; (3) only then measure acceptance and batch-1 cost with the same target and verify the quality of the published base Q4 GGUF, whose parity with BF16 remains unknown. The target remains `engine.c`: llama.cpp would only be a reference/pilot, not the final result. This addendum implies no T4, acceptance, rate, or C-port result.

Full parsing of the 47 metadata keys in both published GGUF headers also shows **all values identical except `general.file_type`**. This includes the same nine `tokenizer.*` fields, including the complete token, token-type, and merge lists and the chat template; the SHA-256 digest of the canonical JSON serialization of each `tokenizer.ggml.tokens` list is `9b70ba2d5504bdce2c15ebaa7b19862f271d5e71c5670e7a1b65947055246fbd` in both, while that of `tokenizer.ggml.merges` is `e5aaaa20b7c5148ade3a4e367fba57608dfcc173720a9c3ad9dceaaea15d4c93`. An MTP-only export can therefore **reuse the published GGUF tokenizer metadata as a candidate**, then verify token-ID parity with the BF16 checkpoint tokenizer; identity of the two GGUF headers alone proves neither that parity nor Q4 quality.

**Local draft-GGUF contract preflight:** [`strat01_gigachat_mtp_gguf_contract.py`](../../../../benchmarks/donor_adaptation/density/strat01_gigachat_mtp_gguf_contract.py) reads only the sidecar JSON manifest, not the 1,6 GB payload, and compares all 210 BF16 keys against pinned shapes. On the actual manifest it returns `metadata_contract=PASS` (210/210); seven [offline synthetic tests](../../../../benchmarks/donor_adaptation/density/test_strat01_gigachat_mtp_gguf_contract.py) cover omissions, extras, shape/dtype/revision, expert completeness, `kv_b` split, and the three root tensors. The deterministic plan specifies 64 experts stacked per projection, `attn_k_b [128,512,32]`, `attn_v_b [512,192,32]`, and direct `attn_q`. In a standalone draft GGUF, `token_embd.weight`, `output.weight`, and `output_norm.weight` must physically exist; MTP embedding/head copies are optional after materializing their respective roots, while the root norm requires the distinct 3.072 B BF16 tensor with SHA `12935320d4033c560cec87fc07cc5d3f0f28ef2cb5b0f509d7a2a05246b0e44b`. The preflight validates **the declaration in the manifest**; it does not recalculate the local payload SHA or write a GGUF. The MTP Q-LoRA graph remains the execution blocker. This `PASS` is not a result for logits, acceptance, quality, or speed.

The [vLLM reference at the revision used by the producer for its benchmark](https://github.com/vllm-project/vllm/blob/600a039f572ac28128750f0463af428c5a260f1a/vllm/model_executor/models/deepseek_mtp.py) clarifies another port prerequisite: the MTP layer receives **the token embedding and the previous target hidden states**, normalizes them separately, concatenates them, applies `eh_proj`, then the MTP decoder and its own head. It is not an independent draft model fed only token IDs. The vLLM loader also checks for MTP-layer weights and fails if quantization omitted them.
