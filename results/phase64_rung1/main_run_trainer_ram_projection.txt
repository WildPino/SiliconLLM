THE RECALL INDEX IS THE ONE TERM NOT MEASURED, and it is named rather than
absorbed into a margin. --recall on builds an IVF-PQ index that stages 1-4 never
built (they all ran --recall off), so no local number exists for it at this
scale. The floor below is set with that in mind.

  --min-host-ram-gib 20     leaves ~3.2 GiB for recall and any term not
                            enumerated above, and still passes on a ~29 GiB
                            Kaggle session with ~9 GiB of slack.

If the measured peak on the first session comes in above this, the reserve is
memmap for ids: it would make the corpus a SHARED page-cache mapping instead of
two private copies, which is strictly better. It is deliberately NOT applied
now -- it is an optimization against a budget we already meet, and it would add
a new variable to the file we are being careful with.

WHAT WAS CHANGED, six sites
--------------------------------------------------------------------------------
  325   ids stay uint16; the cast moves to _i64() at the point of use
  390   np.bincount CHUNKED -- it casts its input to intp internally, so the
        whole-split call would have rebuilt the 18 GiB array that line 325 just
        stopped allocating. The fix at 325 would have survived exactly as far
        as this line.
  544   yt, the KD self-check target batch
  588-597  bpb_on's window stacks and its ragged remainder (val AND P62)
  637-638  the training batch itself
  _i64() is the ONLY widening site, and it widens 32 KB at a time.

ADDED, and each closes a failure this rung has already produced:
  --min-host-ram-gib   startup refusal, container-aware. On Kaggle /proc/meminfo
                       reports the physical HOST, hundreds of GiB, while the
                       container is capped far lower -- a check against MemTotal
                       would read a number it can never spend and pass every
                       time, which is the blind-instrument failure again. The
                       cgroup limit (v2 memory.max, v1 limit_in_bytes) is the
                       authority when present, and host_ram_gib() RAISES rather
                       than returning a sentinel: NaN compares False against
                       everything, so a sentinel would have turned the refusal
                       into a decoration.
  ids-size assert      ts_{tag}.u16 must be exactly 2 x the token count the
                       package's meta declares. This is the floor under
                       collapsing SRC_TAG back into TAG.

The hash is over the WEIGHTS, not over the checkpoint file. A file hash was the
instruction and would have been the wrong instrument: the checkpoint also stores
the argparse cfg, and this change adds --min-host-ram-gib to it, so the file
would have differed for a reason with nothing to do with behaviour. A gate that
fails benignly gets argued with instead of believed.

Throughput is CPU-local and is NOT the 3860 tok/s 2xT4 figure the 145-hour
calendar rests on; the RATIO is the measurement, and it is device-independent
because both runs are the same device with the same recipe.

THREE DEFECTS FOUND ON THE WAY, none of which the gate itself would have caught:

  1. log() was used at line 373 and defined at line 401. The accelerator assert
     called it on its SUCCESS path, so --expect-gpus 2 would have raised
     UnboundLocalError on a CORRECT 2xT4 session and exited cleanly on a wrong
     one -- inverted, in the direction nobody tests. It had never fired because
     no arm before the main run passed the flag. P0/log moved above the guards.

  2. The chunked bincount ran past the split. range(0, ntr, 2^24) without a
     min(..., ntr) on the last slice counted validation tokens as training. The
     val-split assert -- a planted control this trainer already carried --
     refused the run rather than passing the discrepancy through. The control
     caught the fix to the fix. Verified after: chunked == direct, 473,531,343
     bytes against 473,531,343 declared.

  3. A MOVING REFERENCE, created from the other side. The trainer was edited
     while the gate was comparing it: run A had already launched against the
     commit, and runs B and C would have read a different file than A's
     counterpart. Killed and relaunched from a settled tree. Same defect as
     --commit HEAD, produced by moving the object under test instead of the
     reference.
